# AI活用システム セキュリティ規約 例外条項案

> 位置づけ: 院内セキュリティ規約への挿入案と、一般的なクリニックで運用できる範囲に絞った別紙運用細則。
> この文書は Human CTO / 情報システム管理者 / 監査担当者の判断材料であり、単独で導入承認を意味しない。
> 由来: [Issue #161](https://github.com/akaza-lab-org/HealthCheck-OS/issues/161)

---

## 基本方針

この例外条項は、医療情報や個人情報を無制限にクラウドAIへ送信するためのものではない。

目的は、現行規約の「AI送信禁止」「クラウド送信禁止」を維持したまま、次のような狭い条件を満たす院内AI活用だけを管理下で認めることである。

- 法人契約または法人管理下のクラウドAIサービスを使う
- 送信する情報を業務上必要な最小限にする
- 直接識別子は送信しない、または送信前にマスキングする
- 送信経路、端末、責任者、ログを院内で説明できる状態にする
- 新しいデータ種類や画像送信は個別承認に回す

小規模クリニックでは、高度なネットワーク制御や常時監査を最初から前提にすると継続運用できない。したがって、規約本文は短くし、実務は「別紙: AI外部送信運用細則」で管理する。

---

## 規約本文 挿入案

> 院内AI活用システムにおいて、情報システム管理者が承認した法人管理下のクラウドAIサービスを利用する場合に限り、業務上必要最小限のデータを送信できる。送信にあたっては、患者を直接識別できる情報を除外またはマスキングし、利用端末、利用サービス、送信データの種類、ログ保管、定期確認の方法を別紙「AI外部送信運用細則」に定める。

この本文には、特定サービス名、リージョン名、モデル名、詳細なログ仕様を書かない。これらはサービス仕様変更で変わりうるため、別紙または運用台帳で管理する。

---

## 別紙: AI外部送信運用細則

### 1. 送信データの考え方

送信してよいのは、事前に承認された機能で作成される、業務上必要最小限のデータに限る。

初期運用で認めるデータ:

- マスキング済みまたは直接識別子を除外したテキスト
- 院内アプリが生成した、患者を直接識別しない処理用テキスト
- エラー調査用のログ要約。ただし、氏名、カルテ番号、電話番号、生年月日、住所、保険者番号、端末秘密を含めない

送信してはいけないデータ:

- 氏名
- カルテ番号、受診者番号、患者ID
- 電話番号
- 生年月日
- 住所
- 保険者番号、記号番号
- 未加工の電子カルテ画面、全画面スクリーンショット、未加工の帳票画像
- GCP JSONキー、APIキー、接続文字列、端末固有秘密

マスキングに失敗した場合、または識別子が残っているか判断できない場合は送信しない。必要な場合は Human CTO または情報システム管理者が個別に確認する。

### 2. 画像・スクリーンショット

未加工のスクリーンショットや帳票画像は、原則として外部AIへ送信しない。

ただし、業務上どうしても必要な場合に備え、将来の例外余地は残す。例外として扱えるのは、次の条件をすべて満たす場合に限る。

- アプリ自身が生成した定型帳票またはテンプレート由来の画像である
- 切り出し範囲が固定され、氏名欄や識別子欄を含まない
- `crop_guard` 相当の検証で、切り出し位置、寸法、余白を確認できる
- 送信前に人間が目視確認する
- DB反映や診療判断は自動化せず、人間確認を挟む

この例外は、既存の `docs/safety/phi_external_output_safety_rule.md` Rule 3-E と整合する範囲でのみ認める。条件を満たせない画像は送信しない。

### 3. 利用サービスとアカウント

利用サービスは、情報システム管理者が承認した法人管理下のクラウドAIサービスに限定する。

初期標準:

- 法人GCPプロジェクト配下の Vertex AI
- アプリごとにサービスアカウントを分ける
- 権限は `Vertex AI User` 相当に限定する
- JSONキーは配布ZIP、GitHub、チャット、メールに含めない
- JSONキーは既存標準どおり `%USERPROFILE%\.config\gcp\<appname>_key.json` に置く

個人向けAIチャットや私用アカウントに、患者情報、診療情報、院内ログ、端末秘密を投入してはならない。

### 4. 学習不使用・データ保持

規約では「絶対に保存されない」「ゼロ保持」とは書かない。

代わりに、次を年1回またはサービス変更時に確認する。

- 法人契約または公式資料上、顧客データが無断でモデル学習に使用されないこと
- データ保持、監査ログ、不正利用監視の扱い
- 利用しているモデルとリージョンの提供条件

確認結果は、スクリーンショットやメモで管理台帳に残す。小規模クリニックでは、法務文書の完全な解釈よりも、「確認日、確認者、確認した公式資料」を残すことを優先する。

参考: https://cloud.google.com/vertex-ai/generative-ai/docs/data-governance

### 5. リージョン

アプリ側では、可能な範囲で国内リージョンを優先する。

初期標準:

- Vertex AI の location は `asia-northeast1` を優先する
- `global` endpoint を使う場合は、その理由を運用台帳に記録し、Human CTO が承認する
- 利用したモデル、location、確認日を管理台帳に残す

「国内保存を完全保証する」とは書かない。リージョン指定、データ所在地、ログ保持、サービス側処理の保証範囲は同じ意味ではないため、公式仕様と契約条件に従って説明する。

参考: https://cloud.google.com/vertex-ai/generative-ai/docs/learn/locations

### 6. 利用端末

利用端末は、情報システム管理者が許可した端末に限定する。

最低限の運用:

- 許可端末の一覧を台帳で管理する
- 端末ごとにサービスアカウントキーを配置する
- 不要になった端末ではキーを削除または無効化する
- 個人スマートフォンや私物PCからの利用は禁止する

院外からの利用は原則避ける。ただし、管理者が必要と判断する保守作業は、利用者、目的、日時、端末を記録したうえで個別承認とする。

### 7. ログと監査

初期運用では、Cloud Audit Logs の高度な突き合わせを必須にしない。まず、アプリ側で説明可能な監査ログを残す。

アプリ側で残す最低限のログ:

| 項目 | 内容 |
|---|---|
| 日時 | 実行タイムスタンプ |
| 実行者または端末 | Windowsユーザー、端末名、またはアプリ利用者 |
| アプリ名・機能名 | どの機能から送信したか |
| 送信データ種別 | マスキング済みテキスト、ログ要約、定型クロップ画像など |
| モデル名 | 利用モデル |
| location | Vertex AI location |
| マスキング結果 | 成功、失敗、手動確認 |
| エラー | 失敗時の概要 |

送信本文そのものは原則保存しない。保存する場合は、マスキング後の内容に限定し、保存期間を別途定める。

監査頻度:

- 四半期1回を標準とし、難しければ半年1回でもよい
- 監査では全件確認ではなく、数件のサンプル確認でよい
- インシデントやマスキング失敗があった場合は、該当ログを保全して管理者へ報告する

### 8. 承認フロー

日常処理をすべて都度承認にすると運用が止まるため、承認は場面ごとに分ける。

| 場面 | 承認 |
|---|---|
| 初回導入 | 情報システム管理者 / Human CTO |
| 既に承認された定型処理 | 都度承認不要 |
| 新しいデータ種類を送る機能 | 事前承認 |
| 画像送信 | 個別承認 |
| マスキング失敗または判定不能 | 人間確認 |
| サービス、モデル、リージョンの変更 | 変更内容を台帳に記録し、必要に応じて承認 |

## 段階導入

### Phase 1: すぐに始められる範囲

- 法人GCP / Vertex AI
- アプリごとのサービスアカウント
- 許可端末のみ
- マスキング済みテキストまたは直接識別子を除外した処理用テキスト
- アプリ側監査ログ
- 新しいデータ種類は個別承認

### Phase 2: 必要になったら追加する範囲

- 定型帳票の確定クロップ画像
- `crop_guard` 相当の検証
- 人間目視確認
- 画像送信を含む機能ごとの個別承認

### Phase 3: 余力があれば強化する範囲

- Cloud Audit Logs の定期確認
- より厳密な端末制御
- サービスアカウントキーの定期ローテーション
- DLP や組織ポリシーの追加

Phase 3 を初期導入の必須条件にしない。必要に応じて強化する項目として扱う。

## 規約改定チェックリスト

- [ ] 法人管理下のクラウドAIサービスを使用する
- [ ] 個人向けAIチャットや私用アカウントを使わない
- [ ] 送信するデータ種類を事前に定義する
- [ ] 直接識別子を除外またはマスキングする
- [ ] マスキング失敗時は送信しない
- [ ] 許可端末の一覧を管理する
- [ ] サービスアカウントキーを配布物やGitHubに含めない
- [ ] 利用モデルと location を台帳に残す
- [ ] 学習不使用・データ保持条件を公式資料または契約で確認する
- [ ] アプリ側監査ログを保存する
- [ ] 新しいデータ種類、画像送信、判定不能ケースは個別承認に回す

---

## この文書が約束しないこと

- 完全な匿名化の保証
- クラウド側でのゼロ保持保証
- 国内保存の絶対保証
- すべての送信内容の常時監視
- AI出力の医学的正しさ

これらは規約例外では保証できない。必要な場合は、別途契約、技術設計、運用監査、医師による最終確認で扱う。
