# PHI外部送信安全ルール

## 目的

kensin が収集する運用ログ・スクリーンショット等の情報を外部AI（Gem等）に渡す際の、PHI（患者識別情報）流出を防ぐための必須設計ルールを定める。

## 背景

2026-05 のエラーログ収集機能（Issue #3〜#6）の設計・実装過程で確立した。kensin は実名患者DBを扱うため、エラー時のスクリーンショット・入力テキストに患者氏名・カルテ番号・電話番号等が混入するリスクが常に存在する。

---

## ルール

### Rule 1: 外部送信ラインと内部DBラインを完全分離する

PHIを含む可能性のある情報の収集（DB保存）と外部AI送信を、同一フローに乗せない。

```
[内部ライン] スタッフ入力 → DB保存（PHI含む可能性あり）
[外部ライン] マスキング層 → CTO目視確認 → 手動Gem投入
```

- 外部送信専用の関数/エンドポイントを明示的に作る
- 汎用エクスポート関数がそのまま外部送信に使えてはならない

### Rule 2: テキストログは自動マスキング + fail-closed で出力する

外部送信関数は以下を必ず実装する。

```python
# 必須パターン
class MaskingError(ValueError):
    """マスキング後にPHI候補が残った場合に送出する。"""

def export_for_external_review(record_id, db) -> str:
    # 1. patient_id 等の識別フィールドを除外する
    # 2. 自由記述にマスキングを適用する
    # 3. マスキング後にPHI候補が残っていたら MaskingError を raise する（fail-closed）
    # 4. 成功した場合のみ external_safe = True に更新する
```

**必須マスキングパターン（最低限）**

| パターン | 置換後 |
|---|---|
| カルテ番号 `0\d{5}` | `[CHART]` |
| 数字7桁以上 | `[PID]` |
| 電話番号 | `[TEL]` |
| 生年月日（YYYY/MM/DD 等） | `[DOB]` |
| 氏名候補（漢字2-4文字＋さん/様/患者） | `[NAME]` |

カルテ番号フォーマットはシステムごとに異なる。kensin では `0XXXXX`（先頭0+5桁）。

### Rule 3: 画像・スクリーンショットはAI外部送信ラインを設けない

フルスクリーンショットには他患者情報・EMR画面・他アプリが映り込む可能性があり、テキストと異なり自動マスキングが不可能。

- スクリーンショットは **CTOが目視でレビューする専用ライン** に限定する
- スクリーンショットをAI/Gem/クラウドに送信するAPIを作らない
- DBにスクリーンショットのパス・メタデータを登録しない

### Rule 3-E: テンプレート由来・確定クロップ画像の限定的送信許可

Rule 3 の例外として、以下の**全条件**を満たす画像に限り外部AI送信を認める。
1つでも満たさなければ Rule 3 本則（送信禁止）に戻る（fail-closed）。

| 条件 | 要件 |
|---|---|
| 出所 | アプリ自身が生成したテンプレート帳票（整列マーカー＋QR v2付き）のみ |
| 単位 | 原則として、テンプレートまたは専用マーカーから決定論的に切り出した**単一の所見記号セル**のみ。例外として、後述 `result_code_strip`（PHIフリーの派生15行ストリップ）に限り許可。**全画面・全行原画像（生スキャン帯）・患者情報列を含むストリップは不可。** |
| PHI排除 | 氏名/性別/年齢/カルテ番号/受診者番号が座標排除または物理マスクで画像に含まれない |
| 検証 | `crop_guard` が bbox・寸法・余白を検査し、逸脱時は `MaskingError` 相当で送信中止 |
| 識別子 | カルテ番号・受診者番号・batch_id をペイロードに含めない |
| 人間ゲート | 自動投入禁止。人間目視承認を経てのみ DB 反映（Rule 5 を継承） |

**適用範囲外（Rule 3 本則のまま禁止）:** v1/マーカーなし帳票、全画面スクリーンショット、
生スキャン帯（全行原画像）、患者情報列・日付・QRを含むストリップ、上記条件を `crop_guard` で
検証できないあらゆる画像。**※ `result_code_strip`（下記定義の全条件を満たすもの）はこの限りでない。**

**設計思想:** 「許可」ではなく「条件付き例外＋fail-closed」。条件を1つでも欠いたら
本則の送信禁止に戻ることで、ルールの穴を作らない。

由来: Council Issue #381（council:decision）。実装仕様は kensin
`docs/adr/adr_xray_secondary_scan_reflection.md` を参照。

#### Rule 3-E / result_code_strip（PHIフリー派生ストリップの限定許可）

二次読影「判定」列を**ローカルで15行分割し終えた後**に、所見記号セルだけを上から順に
**再構成した派生画像**。次の**全条件**を満たすもののみ Rule 3-E の単位として許可する
（1つでも欠けたら本則＝送信禁止に戻る fail-closed）。

| 条件 | 要件 |
|---|---|
| 由来 | ローカルで行数=15の分割が確定済み（マーカー幾何由来）。≠15 は送信前に fail-closed |
| 内容 | 「判定」列の所見記号セル15個を、ローカル分割後に**再構成した派生画像**。生スキャン帯そのものではない |
| 幾何境界 | 判定列を挟む2本のフィデューシャル罫線の内側に限定。判定日（日付）・周辺アイコン・他列は構造的に含まない |
| 非含有 | 氏名・性別・年齢・受診者番号・院内ID/カルテ番号・**日付**・QR・batch_id・logical_page・row_index・check_id を一切含まない |
| 検証 | `crop_guard` が strip 全体 bbox・15サブセル境界・周辺余白を検査し、逸脱時は送信中止 |
| 応答 | 構造化出力は**上から順に対応する15要素の配列** `[{code, confidence}, …]` のみ。要素数≠15・順序不明・複数候補混在は fail-closed |
| 識別子 | 上記いずれの識別子もペイロードに載せない。行→患者の対応はローカルの QR+manifest+row_index が持つ |
| 人間ゲート | 自動投入禁止。人間目視承認後のみ DB 反映（Rule 5 継承） |

**設計思想:** 「ストリップ一般の解禁」ではなく「**記号列だけの安全な型を1つ名付けて通す**」。
AI が見るのは `d2, b, null, …` の記号列のみで、誰の行かは一切渡さない。生スキャン帯ではなく
ローカル分割後の再構成画像である点が本型の核心。

由来: kensin Issue #438（Plan B-lite / Human CTO 決定）。実装仕様は kensin
`docs/adr/adr_xray_secondary_scan_reflection.md` を参照。

### Rule 4: `external_safe` フラグで外部送信可否を管理する

DBレコードに `external_safe: bool = False` を持たせ、マスキング済みエクスポート関数のみが `True` に更新できる。

```python
# DB モデルに追加
external_safe = Column(Boolean, default=False)

# マスキング関数の中だけで True にする
row.external_safe = True
db.commit()
```

`external_safe = False` のままのレコードが外部送信に使われた場合、アプリ側でエラーを返すことが望ましい。

### Rule 5: 人間ゲートを最終判断に残す

自動マスキングは「機械的に除去できる範囲」に限定される。以下のケースは人間判断が必要。

- 先頭0でない6桁数字（カルテ番号と紛らわしい別の数字）
- 敬称なし氏名（「田中」「山本」等）
- 文脈依存のPHI（「午後の患者」等）

**運用フロー（kensin の標準）：**

```
スタッフ入力（PHI含む可能性あり）
  → 自動マスキング（external_safe = true）
  → CTO目視確認（偽陰性のチェック）
  → CTO手動でGemへ投入
```

自動投入パイプラインは設けない。

## 実装チェックリスト

新たにPHI接触可能なデータを外部AIに送る機能を追加する際は以下を確認する。

- [ ] テキストログに `export_for_external_review` 相当のマスキング関数があるか
- [ ] マスキング失敗時に fail-closed（例外を raise）しているか
- [ ] 画像・スクリーンショットをAI送信するAPIが存在しないか（Rule 3-E の全条件を満たす確定クロップを除く）
- [ ] 画像送信がある場合、Rule 3-E の6条件すべてを `crop_guard` で fail-closed 検証しているか
- [ ] `result_code_strip` 送信時は、要素数=15・全非含有条件・15サブセル境界を `crop_guard` で fail-closed 検証しているか
- [ ] `external_safe = False` をデフォルトにしているか
- [ ] CTO目視確認のステップが運用フローに組み込まれているか
- [ ] マスキング層をバイパスする外部送信エンドポイントが存在しないか（テストで担保）

---

## 適用対象外

kensin 内部の DB-DB 間データ転送や、院内共有フォルダへの保存はこのルールの対象外。院外ネットワーク・クラウド・外部AIサービスへの送信が対象。
